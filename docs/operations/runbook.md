# 运行手册

## 健康检查顺序

1. `web /healthz`：确认 Nginx 进程和 TLS 入口。
2. `market-data /health`：确认 Parquet 已加载并开始服务。
3. `backtest /health`：确认服务进程和 PostgreSQL 查询成功。
4. `/api/market/meta`：确认数据覆盖范围、条数和文件版本符合预期。
5. 固定参数冒烟回测：确认跨服务调用和数据库写入。

公网只暴露第一项和业务 API；内部探针通过 `docker compose exec` 或容器健康检查访问。

## 日志

Rust 服务输出单行 JSON 到 stdout，至少包含时间、级别、服务名、请求路径、状态码、耗时和请求 ID。Nginx 将请求 ID 传给后端。日志不得包含数据库 URL、密码、完整用户配置或大段行情结果。

Compose 默认使用日志轮转，单文件上限 10 MiB、保留 5 个文件。长期留存需要宿主机日志采集，不在 M1 引入独立日志集群。

## 常见故障

### 行情服务反复重启

- 查看容器日志中的 Parquet 路径、Schema 或数据约束错误。
- 对照 `manifest.json` 重新计算 SHA-256。
- 恢复上一个已验证文件并重启 `market-data`。

### 回测返回 502

- 检查行情服务健康与内部 DNS `market-data`。
- 检查请求是否超过 5,000 根及 30 秒内部超时。
- 查询对应回测记录是否已被标记为 `failed`；不要直接删除失败记录。

### 回测一直是 running

- 先确认回测服务日志和进程是否在请求中途重启。
- M1 没有后台作业恢复器；超过 10 分钟的 `running` 记录视为中断，由运维脚本标记失败并写入原因。
- 不重新使用原记录；用户重试会创建新 ID，以保留审计链。

### 数据库不可用

- 回测服务健康检查失败但行情浏览应保持可用。
- 恢复 PostgreSQL 后重启回测服务，让启动迁移重新校验。
- 禁止在故障期间切换到内存持久化。

## 备份与恢复

- 每日使用 `pg_dump` 备份 PostgreSQL，并加密存放在 Compose 主机之外。
- Parquet 不做数据库备份；保存其版本化副本、清单和 SHA-256。
- 每月至少执行一次恢复演练：新 volume 恢复数据库、挂载对应 Parquet、运行基准回测。
- 恢复点必须同时记录应用镜像版本、数据库备份时间和行情校验和。

## 监控阈值

M1 先使用容器健康检查与主机监控。建议告警：容器连续 3 次不健康、磁盘剩余小于 15%、PostgreSQL volume 无法写入、行情元数据意外变化、5xx 比例连续 5 分钟超过 5%。
